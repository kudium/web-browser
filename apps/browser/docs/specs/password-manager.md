# Kudium Browser Personal Data

The current records, group inheritance and AI interfaces are documented in [Personal Data](personal-data.md). This document retains the underlying vault security and authentication details.

Settings → Personal Data shows a table of saved names, websites, accounts and masked passwords without authenticating. Show reveals a password after authentication. Edit, fill and secret mutations also authenticate. Successful authentication lasts for the lifetime of that Preferences window; closing/reopening it, navigation/reload, manual locking, OS screen lock, suspend or application exit revokes access. Revealed values are cleared immediately on a lock notification.

macOS uses LocalAuthentication's `deviceOwnerAuthentication` policy, so the OS chooses Touch ID or Mac login-password authentication. The Swift helper receives no credentials and returns only success/failure. A random vault credential is wrapped using Electron safeStorage backed by macOS Keychain. There is no separate master-password setup for new vaults on supported Macs; first secret access initializes the vault after native authentication. The helper is built for arm64 and x86_64 by predev/prebuild and included with existing assets packaging.

Systems without this native adapter use the master-password fallback. Existing master-password vaults offer a one-time migration requiring the old master password and successful OS authentication. Existing vaults without a browsable index must be unlocked once to populate it. Windows and Linux native authentication adapters are not implemented; they retain master-password access. Cancelled or unavailable native authentication never silently downgrades an OS-backed vault to a password prompt.

Add website logins or autofill profiles, select an open tab, and choose Fill. Fields can match an autocomplete token (name, email, tel, street-address, postal-code), input name, or ID. Mark private fields Sensitive to fill them as masked password inputs. Edit/delete items and change the fallback master password while authenticated.

## Security boundary

- AES-256-GCM authenticates the complete vault payload. Each save gets a fresh 96-bit IV. Master passwords derive a 256-bit encryption key through scrypt (N=32768, r=8, p=1, 32-byte random salt). Fallback master-password changes derive a new key and salt.
- Vault files are written atomically with owner-only permissions. The separate OS-wrapped credential uses owner-only permissions. Failed updates preserve the previous in-memory data. The vault is separate from ordinary browser preferences, history, AI checkpoints, and cloud sync. There is no plaintext fallback or master-password recovery. Back up the encrypted vault and remember the master password; losing either can lose saved credentials.
- The key is overwritten and item references discarded when authorization is revoked. Window-scoped grants are tracked in the main process, not supplied by the renderer; pending authentication cannot grant access after the requesting window closes or navigates. OS screen lock also invalidates pending grants. JavaScript strings cannot provide guaranteed memory erasure.
- Failed unlock attempts receive increasing in-process delays. Offline attackers can bypass those delays: master-password strength matters.
- Only the trusted Settings main frame can manage secrets through IPC. Website frames cannot call this API. The list/status API uses a separate basic metadata index, omits passwords and custom values, and does not grant access to decrypted secrets. Metadata is OS-encrypted at rest when secure safeStorage exists; fallback systems without secure OS storage keep only those browsable basic fields in the index. Index metadata never authorizes filling: destination origin and access grants are checked against the authenticated encrypted payload. an explicit authenticated Edit or Reveal action returns an item only to the trusted editor. No clipboard export.
- Exact HTTPS origins including ports authorize filling. Subdomains and HTTP do not inherit permission. Filling is main-frame-only, rechecks the origin in the destination document, and skips hidden, disabled, read-only and ambiguous inputs. Cross-origin frames, closed shadow roots, signup/reset forms, native applications and automatic save capture are unsupported in this version.
- Ordinary autofill never invokes a form submit. The explicit browser-owned Auto login action can submit one recognized same-origin login form after the user selects Auto login or a saved account in its submenu. Website input/change handlers may still perform site-defined effects. Manual fill requires native confirmation showing the target origin. Sensitive fields are masked, but the destination website necessarily receives filled values; encryption cannot protect credentials from a compromised authorized site.

## AI integration

AI access defaults off. The user must authenticate in Preferences, enable AI access, and authorize each login. Closing Preferences revokes the decrypted vault access used by AI. `list_saved_logins` lists only account references for an accessible tab's exact origin. `fill_saved_login` accepts the reference, requires native approval, and fills locally without returning the password or sending it as a model/tool argument. Existing group scope applies. AI cannot create/edit/unlock the vault, retrieve arbitrary secrets, or use custom profile fields. The result contains only a filled count. Existing password observations omit password input values. A malicious authorized website can echo filled values into visible text; this is an inherent website trust boundary and is not eliminated by local filling.

## Modularity and extension

`src/browser/passwordManager.ts` contains shared DTOs. `src/main/passwordManager/vault.ts` is an Electron-independent encrypted store; `fill.ts` is the self-contained browser adapter; `index.ts` owns trusted IPC, window-scoped authorization, lifecycle locking and page registration. `authentication.ts` owns OS credential protection and the native authentication adapter. `PasswordManager.tsx` is the Settings UI. Browser and AI use the same local fill service.

Future native-app or browser-extension adapters should accept opaque item IDs, validate their target identity locally, obtain user authorization, and return only nonsecret receipts. They should not expose the store's `forFill` method over a general-purpose IPC/MCP endpoint. System-wide autofill, passkeys, shared vaults and sync require separate implementations and security review.

Run the passwordVault/passwordFill tests plus aiToolSchemas/ai tests. `.erb/scripts/password-manager-smoke.cjs` exercises a disposable native Electron profile, HTTPS test pages without networking, trusted/untrusted IPC, minified serialized filling, safe receipts, and origin/lock rejection. `.erb/scripts/password-auth-smoke.cjs` additionally verifies OS-backed initialization (with a fake native prompt), public metadata after closing/reopening Preferences, one prompt per window, repeated secret access, cancellation and OS screen locking. The actual Swift helper is compiled and checked for local authentication availability; tests do not authenticate the human. Neither smoke script touches personal profiles. This is a tested initial implementation, not an independently audited password manager.

## Auto login

The website context menu offers **Auto login** when Personal Data and website autofill are enabled. The action authenticates locally when needed, uses the single saved account directly or exposes multiple accounts in a context-menu submenu, and fills/submits one recognized main-frame username/password form. Login and website knowledge records are supported when both credentials belong to the same record and exact HTTPS origin. Hooks never receive the password.

A current login form takes precedence over a stored route. Otherwise, the action discovers visible same-origin sign-in links or buttons. It ranks the selected account's remembered route first when that route is among the discovered choices, lets the user choose between multiple destinations (such as business/admin and regular login), and falls back to the remembered route when no current destination is found. Routes are hints, never path-based authorization; changed login pages remain usable. Successful login saves the route per account and group, removing transient query/hash data. Saving a newly observed login also records the original submitted login page, rather than the destination dashboard.

The action returns to the original URL only after observing a visible Sign out/Log out control and no login form. It stops for ambiguous forms/buttons, new-password/signup forms, OTP/CAPTCHA fields, cross-origin redirects, revoked access, or unsupported multi-step flows. It submits once; if success cannot be confirmed, the page remains open for the website to show its own error or verification UI, without an additional browser dialog. This is on-demand login assistance, not a universal session-expiry monitor. Current signals are visible login forms/sign-in destinations and signed-in controls; sites with different or localized signals may need manual completion.

Validation: `autoLoginDocument.test.ts`, `vaultConsent.test.ts`, existing password/vault suites, and `.erb/scripts/auto-login-smoke.cjs` (production-minified helpers, disposable native WebContentsView and encrypted vault; no network or live credentials).

Auto login menu construction uses an in-memory index of account IDs, titles, usernames, origins, scopes and route hints. It never reads the vault file or decrypts credentials. Startup loads the protected summary off the main thread; successful vault writes refresh the index. The selected account is revalidated after authentication. Discovery and fill each use one effective-record pass rather than rescanning the vault per account. Page readiness and sign-in confirmation use navigation events and a debounced observer for relevant DOM changes, with bounded timeouts and no periodic polling.

Passive autofill availability uses a separate nonsecret field-metadata index, including group overrides and website priority. Locked status reuses its loaded summary; background lock expiry does not read storage. Note lists and settings refresh through saved-data change notifications. Save-login detection observes only a pending attempt, using DOM changes and bounded settling timers. See [UI refresh performance](ui-refresh-performance.md) for the implementation plan and retained compatibility sampling.

Opening autofill suggestions or browsing saved data does not request biometric authentication. These responses expose only nonsecret values and blank placeholders for protected fields. Selecting a protected field or filling a saved login authenticates before reading or filling secrets. A master-password-only vault still requires its encryption key to be unlocked before nonsecret values can be read; OS-backed vaults can decrypt a scoped operation without granting lasting secret access.

Focusing a recognized usable input opens its suggestion dropdown automatically while retaining input focus for typing. The trigger can reopen the dropdown; the lightning shortcut explicitly switches to whole-form filling. Returning focus after choosing a value or dismissing the dropdown does not reopen it automatically.

The browser-wide **Open suggestions on focus** preference defaults on and is available in Personal Data’s **Autofill & access** controls. Turning it off disables automatic dropdown opening while preserving manual trigger and whole-form shortcut actions; existing pages receive changes immediately.
