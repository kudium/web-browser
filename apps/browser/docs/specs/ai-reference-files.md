# AI references and reusable files

Tabs and groups offer **Add to AI** in their context menus. The action opens the Assistant and copies an ID reference into the shared attachment strip. It does not move tabs or change AI access. Multiple references are supported, with existing deduplication and an eight-reference limit. An out-of-scope reference requires the user to choose the appropriate access scope.

Mention suggestions prioritize groups, using readable names, GroupIcon and exact saved-tab counts. Typing `@group/` searches that group's tabs. References resolve to browser-owned IDs at send time; stale or inaccessible references fail rather than receiving a global answer. Each group's metadata includes its exact non-archived tab count. For a chat task with one referenced group, unfiltered `list_tabs` defaults to that group; `groupId:null` explicitly requests all permitted tabs. This subject preference does not change tab-access permissions or external MCP scope. Tab listing builds its group/page indexes once per call.

The composer accepts Markdown and offers a sanitized preview. Both human and assistant messages render Markdown. Group mentions become compact clickable references with full names/counts on hover. Their shared picker supports focusing the group, searching saved tab titles/URLs, focusing a tab, or using a tab to narrow the draft context. Picker output is capped at fifty rows; search refines larger groups. Code, HTML and unsupported references remain inert.

Original chat files remain in bounded, window-local memory under opaque IDs. Limits remain eight files, 20 MB each and 30 MB combined. The AI receives extracted document text/normalized image content for an initial review, then a small catalog of available file IDs for follow-up tasks. Original filesystem paths and original byte payloads are not injected into provider messages. A reusable-files disclosure survives renderer reconnects and offers explicit Forget actions.

`upload_chat_attachment` resolves an opaque ID locally and calls the existing reviewed website-upload adapter. It retains all existing tab, frame, origin, snapshot, cancellation and native approval checks. Uploading a file does not submit the website form. Uploaded originals use a shared bounded local cache for chat attachments and saved Personal Data documents. Chromium reads File objects lazily, so these files remain available until navigation commits, the page closes/crashes, or the browser service disposes. This permits a subsequent, separately authorized multipart submission. The private cache is recovered after an app crash on the next service initialization.

Documents offer **Save to Personal Data** before or after sending. A native review identifies Browser-wide or the selected group's stable Personal Data scope and offers Save privately or Save with AI access. Storage reuses local extraction and the encrypted vault; adding through OS-backed storage does not grant secret access. Master-password fallback requires unlocking the existing vault. Private documents retain their AI setting through saving, editing and migration; ordinary key/value records keep their existing defaults. Original images can be uploaded, but persistent Personal Data document saving supports PDF, DOCX, TXT and Markdown.

Verification uses disposable profiles, a local job form and a deterministic local provider. It checks original-byte fidelity, native upload review, no automatic submission, a separate multipart submission, committed-navigation cache release, encrypted private saving without secret grants, cancellation, follow-up catalogs, exact group counts, clicked chat references, group/tab search, multiple context requests and production native-menu entry points. OS chooser/review responses are stubbed; live job applications and live commercial model behavior are not part of these checks.
