# Native Enter and keyboard-target validation — November 7, 2026

Enter was serialized without character text, producing rawKeyDown instead of a
native character-bearing keyDown. Chromium could deliver keydown/keyup without
keypress or default form submission. A diagnostic with hidden and visible native
windows confirmed that carriage-return text restores keypress/default behavior.
The full MCP path also showed intermittent lost keydown delivery when focusing
immediately before dispatch.

`aiKeys.ts` now supplies `\r` for Enter and Shift+Enter; Control/Alt/Meta chords
continue to omit text. The existing keyUp clears text, so a textarea receives
one newline rather than a second insertion. The key action now performs a second
isolated renderer evaluation after focus. It revalidates the original snapshot,
node identity, attributes/protected type and current focus without refocusing or
scrolling the field. This separates focus and input dispatch across renderer
calls and blocks fields changed during focus. No fixed delay, synthetic DOM key
event, native-window focus borrowing or extra permission question was added.

## Native observations

`enter-key.json` records actual registerAI, encrypted synthetic vault, official
MCP SDK, hidden native WebContentsView, Chromium keyboard events and loopback
POST bodies on Electron 45/macOS arm64. The page's submit handler prevents
navigation and fetches the synthetic form value. Native approval choices are
controlled. Baseline substitutes exact retained pre-change `ai.ts` and
`aiKeys.ts`; other dependencies use current source and are hashed.

| Case | Before | After |
| --- | --- | --- |
| 14 approved Enter attempts (public, private and 12 repeated private attempts) | 0 submits /0 POSTs | 14 submits /14 POSTs; one per attempt |
| Shift+Enter in a textarea | No newline | One trailing newline |
| Page cancels Enter during keydown | 0 submits /0 POSTs | Same; cancellation honored |
| Control+Enter in textarea | No character insertion | Same |
| Private Enter review declined | Error; 0 key commands/events/POSTs | Same; one existing review |
| Field becomes readonly during focus | Tool accepts; 2 key commands | Tool rejects; 0 key commands |

All delivered after keyboard events are Chromium-trusted. Private accepted
requests still require one local review; public Full-access requests require
zero reviews. The input guard remains installed; these CDP events do not pass
through Electron's native before-input-event hook. This does not identify or
verify physical-human input.

The normal key action still sends exactly two Input.dispatchKeyEvent commands.
It adds one renderer evaluation for target validation. That is a measured command
count tradeoff, not a claimed whole-app speedup. The native result covers the
listed attempts, rather than a universal timing guarantee. Unit tests verify
modifier/text serialization and that validation rejects lost focus or changed
attributes without refocusing another control.

Final source passes all 142 suites /727 tests, lint/TypeScript and production
build. `enter-key-verification.json` binds probe/source, raw results, command logs
and the immutable IPC inventory with SHA-256 hashes. The native probe is included
in the desktop runner.

## Remaining gates

The original `ai-activity-smoke.cjs` UnknownVizError/pointer regression and broader
sidebar focus issues remain separate unresolved gates. This test does not cover
physical keyboard input, all iframe/OOPIF layouts, every shortcut, DOM races after
final validation, key release during interruption, actual OS authentication,
signed distribution or other platforms. Private-data provenance and downstream
worker/frame/existing-channel containment remain open. Production readiness is
unproven.
