# App-list state processing — November 6, 2026

Raw evidence: [app-state.json](app-state.json). The `before`, `after` and
`confirmation` entries use the final probe. Older exploratory executions remain
in `previousRuns`, with their original source/probe hashes.
Quality-gate output tails and source/production-bundle identities are recorded
in [app-state-verification.json](app-state-verification.json).

## Problem and decision

`AppManager.getAll()` parsed, validated, reconstructed and migrated the entire
saved list on every call. `useState(AppManager.getAll())` also evaluated that
read on every render, even when React ignored the initializer's result. Five
hook consumers performing 30 unrelated updates caused 150 full-list parses.

The manager now caches the normalized JSON for the exact successful saved
string. Each read still checks localStorage and parses an independent copy, so
callers can edit returned records without changing another caller or persisted
data. The cache skips repeated validation, object reconstruction and group-name/
slug migration. Different, removed or unavailable storage invalidates it. Failed
migrations and damaged originals are retried rather than hidden behind a cache.
Caching requires the persisted string to match the normalized result; manually
formatted or otherwise noncanonical JSON may continue through the full path.

The hook now uses a lazy state initializer. It subscribes before checking whether
storage changed since the initial read, catching writes before subscription.
Unchanged mounts avoid an extra state update; ordinary update events continue to
reread authoritative storage. No state library, persistence format or permission
policy changed. Every write still runs the existing current group-access check.

## Measurements

Actual source modules bundled by esbuild, Node 22.23.1, React 18 test renderer,
macOS arm64, synthetic in-memory localStorage. The raw report includes exact
runtime, hardware and transitive bundled-source hashes. No personal profiles or
credentials are used. Build/setup are excluded from timing. Each dataset has
30 warmup reads, then 30 bursts of 300 reads, followed by five mounted consumers
and 30 unrelated prop updates. The confirmation repeats the after workload in
a fresh Node process.

| Saved records | Median burst of 300 reads, before → confirmation | Median update of five hook consumers, before → confirmation |
| --- | --- | --- |
| 1 | 0.691 → 0.181 ms | 0.048 → 0.040 ms |
| 10 | 5.112 → 1.284 ms | 0.125 → 0.037 ms |
| 50 | 24.763 → 5.902 ms | 0.445 → 0.038 ms |
| 1,000 | 464.233 → 113.053 ms | 8.036 → 0.082 ms |

Warm read bursts are about 74–76% shorter at their medians. At 50 records,
the burst p95 changed 26.144 → 6.229 ms; at 1,000 it changed
505.030 → 115.913 ms. Both before and after still performed 9,000 storage reads
and JSON parses for the explicit 9,000-read workload. The hook's unrelated
updates performed 150 → **0** app-list parses. Other render work and selected-tab
storage reads remain; this is not a claim of zero work per render.

Five consumer mounts perform five parses in both final versions. The new
freshness checks increase their synthetic storage reads from 15 to 25. A single
first uncached read at 1,000 records took 1.529 ms before and 2.665 ms in the
confirmation, reflecting extra cache construction. These cold observations are
single samples, not five measured app launches or a proven startup regression.
The cache also retains normalized JSON in memory; process memory impact has not
been measured. Small sub-millisecond timing differences are noisy.

The measurements cover saved records, **not live website tabs**. They exclude
Chromium painting, actual Electron IPC/localStorage disk work, website processes,
idle CPU/GPU, startup and total process memory. Whole-app 1/10/50-tab profiling
remains a separate required gate.

## Correctness and verification

The probe dispatches a write during a layout effect, before the consumer's
passive subscription. All four baseline datasets retained the old `Changed`
name; all final datasets displayed `During mount` without requiring another
event. The first attempt at this probe expected a string without the dataset
count, while the actual rendered string included it; the assertion was corrected
and the complete before/after comparison rerun. This was a fixture correction,
not a product failure or a counted passing result. A later evidence check found
the generated temporary entry file included in the dependency list because
macOS resolved `/var` through `/private/var`. The final probe compares real paths
to exclude that generated file, and all phases were rerun. Previous reports
retain their original metadata; they do not establish permanent source-file
availability for that temporary entry.

`appState.test.tsx` covers direct replacement/clear, unavailable storage, nested
mutation isolation, failed damaged-data recovery followed by successful retry,
cross-window-style broadcasts, subscription cleanup and the mount race.
Existing recovery, UI, group and browser regressions remain enabled.

Final product verification:

- `npm test -- --runInBand`: 131 suites / 664 tests passed.
- `npm run lint`: whole-project style and TypeScript gates passed.
- `npm run build`: production main/renderer bundles built successfully.
- Actual Electron `browser-ui-smoke.cjs --organization-only`: 26 favorites,
  rename, folder drop preserving session identity, persisted collapse,
  keyboard navigation and narrow layout passed.
- Actual Electron `browser-ui-smoke.cjs --opener-flow-only`: adoption/opener
  messaging, early closure, timeout/late-ack refusal, keyboard/Archive restoration,
  download recovery and AI handoff passed.

Desktop checks load the production React renderer and real browser manager in
the existing disposable-profile harness. Some main-module services are mocked;
these are functional regressions, not signed installed-app verification or
whole-app performance measurements. Existing Electron safeStorage deprecation
warnings remain and do not establish future-version compatibility.

This change does not close the IPC audit, shared-data ownership redesign,
selective subscriptions, pagination, large-data query or packaged release
requirements.

## Reproduction and rollback

From the repository root:

```sh
node .erb/scripts/app-state-benchmark.cjs before
node .erb/scripts/app-state-benchmark.cjs after
node .erb/scripts/app-state-benchmark.cjs confirmation
npm test -- --runInBand
npm run lint
npm run build
```

The `before` command loads the two state modules from Git revision
`de2eae3bdf2f346d66dc91a6ef5aeda9581c0603` into a temporary bundle, without editing
the checkout. Other transitive sources are the current worktree and are hashed
in each report; changing them requires a new fair comparison. Subsequent runs
preserve replaced reports in `previousRuns`. The temporary bundle is removed
and its React consumers/listeners are unmounted.

Rollback only requires reverting the cache and hook changes. Saved JSON and its
recovery copies retain their existing format; no database migration is involved.
